# Agent dashboard redesign — plan v3.2

Status: v3.1 after three Codex review rounds (v1, v2, v3: CHANGES REQUESTED;
v3 findings applied without a fourth round). See "Review changes". Not built
yet.

This plan maps the Claude Design project "Dashboard Redesign" (Cockpit, Agent
detail, Delivery, 5 cockpit states) onto the local stack in
`tools/agent-monitoring`: collector `scripts/epic/monitor.py`, generator
`scripts/epic/dashboards.py`, Prometheus, Loki, Alloy, Grafana 13. The
design's panel spec is copied into the appendix; this file is the acceptance
source.

## Goal

The dashboard answers, in this order:

1. Do I need to act?
2. What is each agent doing, and does one wait for the other?
3. Is the loop healthy (ticks succeed, not fail, time out or hang)?
4. How far along is the epic, and how fast?

## Problems today

- "Last exit" shows a raw red `1`. Exit 1 is often a `gh`/`git` failure in the
  runner, not a model failure. Exit codes are never named.
- The last exit comes from a 128 KiB log tail. No tick history, failure rate,
  durations or tokens.
- Collected data is not shown: `codex-backoff.json`, `claude-permissions.log`,
  Codex `tokens used`.
- No handoff view and no trends. Wasted space; truncated leaf titles.

## Rules

- **Trust boundary.** Runner logs mix runner output with model output,
  prompts and command output, so a line in them cannot prove who wrote it.
  - Preferred tick data comes from a new runner-written events file (PR 2).
    It is trusted for Codex (its sandbox cannot write there). For Claude it is
    best effort too, because write isolation from the model is not proven.
  - Data parsed from the old logs is **best effort**, marked
    `source="log"`, and used only for ticks before the events file exists.
  - Metrics carry only counts, timestamps, numbers, fixed enums, and
    URLs/titles normalized by the existing `action_labels()` / GitHub
    snapshot. Never exported: `gh`/`git` arguments, permission commands or
    reasons, backoff summaries, model summaries, raw log lines.
- Stale data shows grey "unknown", never green or zero. Alerts are gated on
  freshness **and** read health of every source they use.
- Dashboards stay generated by `dashboards.py`; the JSON-up-to-date test stays.
- The runners' selector input (`next_action.fetch_state()`) and the runner log
  format do not change.
- Daily and hourly values use Europe/Berlin local time, computed in the
  collector (DST days have 23 or 25 hours).

## Tick model

A tick runs from start to finish of one runner invocation that holds the lock.

- Running now: only `owner.json` + PID liveness (existing `runner_metrics`).
  `max_age` is the whole budget (selector + model + kill grace); exported as
  `epic_tick_budget_seconds`.
- Lock contention happens before the tick starts (`claude-tick.sh:41–79`);
  `tick: locked; …` lines are contender events, not ticks.
- A tick with no finish before the next start is `interrupted`.

Outcome enum, severity order for "worst": ok 1 < blocked 2 < timeout 3 <
killed 4 < interrupted 5 < error 6.

Phase enum (where a failed tick stopped), runner-owned, replaces free-text
reasons: `lock`, `select`, `gate`, `backoff`, `model`, `result`, `verify`,
`record`, `unknown`.

### Events file (preferred source, PR 2)

Both runners append one JSON line per event to
`$state_dir/<agent>-ticks.jsonl` (atomic single `printf` of < 4 KiB, so lines
never interleave):

```json
{"v":1,"event":"start","tick":"2026-09-28T15:39:39Z","pid":38604}
{"v":1,"event":"finish","tick":"2026-09-28T15:39:39Z","at":"2026-09-28T15:47:10Z","exit":0,"outcome":"ok","phase":"model","action":"review","pr":436,"issue":null,"tokens":89040}
```

- `outcome` and `phase` are set by the script, which knows each path:
  Codex `record` returns 3 → `blocked`, 75 → `error`/`result`; selector
  failure → `error`/`select`; `run_bounded` 124/143 → `timeout`/`killed`.
- `tokens` (Codex): the runner reads the last `tokens used` count from the
  session's own captured output (numeric only). Best effort; `null` if absent.
- Who can write the file: Codex's sandbox write roots do not include
  `~/.local/state` (seen in the session header). For Claude this is **not**
  proven: `permission_gate.py` only answers prompts; it does not block file
  writes. Remaining risk, accepted for a local read-only dashboard: Claude
  event rows carry `source="events_unverified"`, Codex rows `source="events"`.
  The collector checks what it can check after the fact (the lock files are
  deleted when a tick ends, so no pid check): schema and enums, one finish per
  start, finish after start, start times increase. Invalid lines are counted
  in `epic_tick_events_rejected_total` and ignored.

### Legacy log parser (best effort, PR 1)

For history before the events file:

- `tick: started <ISO> repo=…` to `tick: finished exit=N` (exact whole line).
- Exit 0 ok · 124 timeout · 143 killed · 75 blocked **only if** the tick has
  `backoff: model reported blocked: …`, else error · other non-zero error.
- Tokens: `tokens used` then `^[0-9][0-9,]*$`.
- End time: the legacy finish line has none. If the collector reads the
  finish in a live increment (after the baseline), end = read time (up to 5 s
  late, marked `end="observed"`). For history before the baseline, end and
  duration are unknown (`-1`, shown as "–"). Start times always come from the
  start line.
- Phase: `select` if the tick has `CalledProcessError: Command '['gh'`, else
  `unknown`.
- Tests include exact, unindented forged markers inside model output to
  document that the legacy path can be fooled. That is why it is labeled best
  effort and replaced by the events file.

## PRs

Order: PR 1 → PR 2 → PR 3 → PR 4. PR 3 is independent of PR 1–2. PR 4 needs
all three. Every PR is safe to merge while the old collector still runs:
nothing a runner writes changes the old log format.

### PR 1 — Collector: tick ledger, counters, budget

- New `scripts/epic/ticks.py`: legacy parser, outcome/phase enums, ledger,
  incremental reader, checkpoint. `monitor.py` uses it instead of the 128 KiB
  tail. `epic_last_observed_exit_code` stays until PR 4.
- Both runner scripts print `tick: finished` **before** releasing the lock
  (it was after). The line format does not change; the order guarantees the
  next tick's start line comes after the previous finish.
- Incremental reading: checkpoint
  `{inode, size, offset, partial_line, ledger, totals, coverage_start}` in
  `runtime/ticks-<agent>.json`.
  - Order per cycle: read new bytes → update ledger and totals → write
    checkpoint atomically → publish metrics. The checkpoint holds offset
    and ledger together, so a crash before the write replays only ticks
    that were never saved; nothing is counted twice. Tick identity is the
    position in the log, never the wall-clock start (clocks can go back,
    starts can share a second). The runners only append; a file that
    repeats old lines after rotation is not supported (its ticks count
    again).
  - Unfinished last line and split UTF-8 kept in `partial_line`.
  - Truncation (same inode, smaller size) or rotation (new inode) → re-read
    the file; ticks already in `totals` are not counted again.
  - Counters count only ticks whose finish line lies **after a byte
    baseline**, not after a time (legacy finish lines have no timestamp). On
    the first start and after a corrupt or missing checkpoint, the baseline
    is the current end of each log, `coverage_start` = now, and counters
    restart at 0; finishes before the baseline (old history) are **not**
    added to counters. Rotation or truncation sets the baseline to 0 of the
    new file (all its lines are new). The baseline is stored in the
    checkpoint. So a recovery never looks like new activity to
    `increase()` (a drop to 0 is a normal reset). The recovery time is
    published as `epic_tick_coverage_start_timestamp_seconds`.
  - History panels do not use counters: the ledger rebuilds the gauges
    (today counts, durations, hourly worst, last 20 ticks) from the log.
  - `totals` are stored separately from the ledger, so ledger eviction
    (2 000 ticks) never lowers them.
- Every `agent × outcome` counter series exists from the first publish with
  value 0.
- Hourly and daily aggregates come from the ledger, in local time.

Metrics (runners.prom; `Metrics` gains `kind="counter"`):

| Metric | Type | Labels | Meaning |
|---|---|---|---|
| `epic_ticks_total` | counter | agent, outcome | ticks finished after `coverage_start` (new activity only) |
| `epic_tick_coverage_start_timestamp_seconds` | gauge | agent | oldest tick the counters cover |
| `epic_tick_budget_seconds` | gauge | agent | `max_age` of the running tick |
| `epic_tick_last_outcome` | gauge | agent | severity of the last finished tick (held) |
| `epic_tick_consecutive_failures` | gauge | agent | trailing error/timeout/killed/interrupted; blocked skipped, ok resets |
| `epic_tick_last_info` | gauge | agent, outcome, exit, phase, action, target, source | value = end timestamp |
| `epic_ticks_today` | gauge | agent, outcome | local day |
| `epic_tick_duration_today_seconds` | gauge | agent, quantile (0.5, 0.95) | ticks with known end |
| `epic_tokens_today` | gauge | agent | Codex only; no Claude series |
| `epic_tick_hour_worst` | gauge | agent, day (YYYY-MM-DD), hour (00–23, the repeated autumn hour is `02b`) | worst severity in that local hour, last 7 days; buckets are keyed by UTC hour start, so a DST day has 23 or 25 cells; no series for hours without ticks |
| `epic_tick_info` | gauge | agent, tick, action, target, outcome, exit, phase, tokens, source | last 20 finished ticks; labels fixed once finished; value = duration s or -1 |

Cardinality: `epic_tick_info` ~160 new series/day; `epic_tick_hour_worst`
≤ 336 live series with one new series per agent-hour; about 10 k series over
30 days. No `sample_limit` is added (a full-size scrape reaches about 6 400 samples; failing the whole scrape is
worse than the risk).
A max-size fixture test (500 items, 200 open and 600 merged PRs, 2 000-tick
ledgers over 7 days) measured 6 357 samples; it asserts one scrape stays
under 7 000.

Tests (`test_ticks.py`, `test_monitor.py`): each outcome incl. 75 with and
without the blocked line; interrupted; contender lock line; tokens with
commas; exact forged markers (documented best effort); incremental read with
appends, split UTF-8, truncation, rotation, restart between read and
checkpoint, corrupt checkpoint, missing file, unchanged file; first
occurrence of an outcome; totals survive eviction; recovery does not add old
ticks to counters; local midnight; spring and autumn DST days (23 and 25
cells, `02b`).

### PR 2 — Runner events file, backoff, permission gate

Runners:
- `scripts/epic/claude-tick.sh`, `.codex/codex-tick.sh`: write start/finish
  events (format above). The existing log lines stay unchanged.
- `.codex/tick_backoff.py`: new entries store `until = at + ttl`; `check`
  uses `until` when present, else `at + --ttl`. So the stored expiry is what
  the runner obeys.

Collector:
- Prefers events for ticks after the first event; legacy parser for older
  ones. Tick `source` label: `events` or `log`.
- `epic_backoff_info{agent, target, head, estimated, current_head}`: active
  entries only; value = `until` ("cooldown expires"). `estimated="true"` for
  old entries without `until` (uses the runner default 900 s).
  `current_head` = `true`/`false`/`unknown`, from the last successful GitHub
  snapshot. The latest entry per `(target, head)` wins.
- `epic_permission_decisions_total{agent, decision}` counter from an
  incremental read of `claude-permissions.log` (same checkpoint rules).

Alloy:
- New stream for `claude-permissions.log` with label
  `agent="claude-permissions"`. Existing exact `{agent="claude"}` queries do
  not change.
- `stage.regex` `^(?P<ts>\S+) (?P<decision>allow|deny) ` → `stage.timestamp`
  (`source = "ts"`, `format = "RFC3339"`) → `stage.labels` (`decision`).
- `stage.drop` with `older_than = "167h"`: Loki rejects lines older than one
  week by default, so older lines are dropped on purpose. The collector
  counter still covers the full file.

Tests: events written on every runner exit path (ok, blocked, invalid
result, selector failure, timeout, kill) in `test_claude_tick.py` and
`.codex/tests`; backoff `until` used by `check`; collector event/legacy
merge; event validation (orphan finish, finish before start, bad enum,
out-of-order start) incl. events read after the tick's lock is gone and
after a collector restart; backoff estimated/current_head/dedupe/expiry;
permission counter.

### PR 3 — Monitor-only GitHub delivery and handoff data

- New `monitor.fetch_delivery()` in the monitor only, own snapshot file and
  timestamp `epic_delivery_snapshot_timestamp_seconds` (panels gate on it;
  fresh selector data never makes stale delivery data look fresh).
  - Open PRs: `createdAt`. PRs merged in the last 14 days: `createdAt`,
    `mergedAt` and full comments via the paginated REST call with the same
    completeness check as `fetch_state()` (`next_action.py:427–443`).
  - Review stats are "current": merged PRs in the window are revalidated
    every 30 min (≤ about 30 PRs); new merges are fetched on the next poll.
  - Incomplete history → `epic_delivery_complete 0`; values are not guessed.
  - Failure keeps the last delivery snapshot.
- Handoff waits (`runtime/handoff.json`):
  - A PR is "waiting for review" when `decide(reviewer)` includes `review`
    for it (same eligibility: not paused, not draft, not escalated, no valid
    verdict for the head).
  - `first_seen[(PR, head)]` is set on the first successful observation. It
    is removed when a successful observation shows the PR not waiting (any
    reason, same head or not). A failed observation changes nothing.
  - `epic_handoff_wait_seconds{waiter, waits_for, target}` = now −
    first_seen ("observed waiting time").
- `epic_handoff_stalled` = 1 when both agents have an observed wait
  > 30 min, the loop is not paused, both runner states are `inactive`
  (not running, orphaned, overdue or unknown), and all sources are fresh.
  Called "suspected stalled handoff".
- Delivery metrics: `epic_area_leaves{area, agent, state}`,
  `epic_merged_prs_day{agent, day}` (14 days), `epic_pr_flow_info{target,
  executor, reviewer, opened, state}` (last 14 PRs, value = review rounds),
  `epic_review_rounds_median`, `epic_time_to_merge_median_seconds` (last 7
  days). Review rounds = valid verdict comments by the reviewer
  (`next_action.verdicts`).
- Tests: first_seen per head, cleared on draft/escalation/verdict, kept on a
  failed poll, survives restart; stalled rule with pause, running, unknown and
  stale; incomplete history; revalidation after a comment edit; empty
  window.

### PR 4 — Dashboards and alerts

Three dashboards (grid, colors, thresholds from the appendix):

- `epic-agents` **Cockpit** (keeps the home URL).
- `epic-agent` **Agent detail**, variables `agent` (claude|codex) and
  `search`. `epic-agent-claude` / `epic-agent-codex` become a text panel
  linking to `epic-agent?var-agent=…`.
- `epic-delivery` **Delivery**.

Panel semantics:

- **Last 20 ticks**: Stat on `epic_tick_info` (instant, table), sort by
  `tick` ascending, show `outcome`, reduce "All values", limit 20, color mode
  background solid, mapping outcome → color.
- **Tick outcomes · 24 h**: per agent two rows: "Activity" from
  `epic_runner_state`, and "Last outcome (held)" from
  `epic_tick_last_outcome`.
- **Outcome per hour · 7 days**: Table on `epic_tick_hour_worst` (instant),
  transformation "grouping to matrix" (rows `day`, columns `hour`, value =
  severity), cell color by value mapping. Empty cell = no tick. No PromQL
  tricks; local time from the collector.
- **Tick history**: table on `epic_tick_info` sorted by `tick` descending;
  outcome colored; target links to GitHub; phase shown; data link to Loki at
  that tick's start. `source="log"` rows show a small "best effort" marker.
- **Errors only**: Loki `{agent="$agent"} |~ "^(Traceback|fatal:|tick:
  finished exit=[1-9]|backoff: )"`.
- **Permission gate per hour** and **Last 10 denials**: queries use
  `agent="$agent"` / `{agent="${agent}-permissions"}`. Codex has no data →
  "not reported by this runner" in grey.
- **Tick elapsed**: `epic_tick_elapsed_seconds / epic_tick_budget_seconds`.
- **Burn-up**: `sum by (area)(epic_area_leaves{state="checked"})` stacked +
  totals dashed. History starts at deploy.
- Guards: local panels `LOCAL`, GitHub panels `GITHUB`, delivery panels
  `DELIVERY` (`time() - epic_delivery_snapshot_timestamp_seconds < 600`).
- "Needs Anton" = needs-anton labels + pause + stalled handoff + any agent
  with ≥ 3 failures in a row.

Alerts (`alerts.yml`):

- `AgentFailingRepeatedly`: `epic_tick_consecutive_failures >= 3` and local
  fresh and `epic_runner_read_success == 1` for that agent; for 1 m.
- `AgentHandoffStalled`: `epic_handoff_stalled == 1` and local fresh, GitHub
  fresh, `epic_github_collection_success == 1`; for 5 m.
- Existing stale-source alerts stay. `promtool test rules` for firing, stale,
  missing, read failure and recovery.

Tests (`test_dashboards.py`): uids; agent page uses only `$agent` (incl.
`${agent}-permissions`); redirects; transformations match used labels; JSON
up to date. Manual: compare with the design at 1600 and 1280 px; reproduce
the 5 cockpit states with fixture state files.
